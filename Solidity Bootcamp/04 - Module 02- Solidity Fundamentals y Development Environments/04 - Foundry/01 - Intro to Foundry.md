# Intro to Foundry

This tutorial guides you through building a minimal Foundry project by creating a staking application, teaching you how to effectively work with Foundry for smart contract development.

[Video: Intro to Foundry | The FASTEST Smart Contract Framework](https://www.youtube.com/watch?v=fNMfMxGxeag)

**Transcript for the AI**

When building smart contracts, key considerations include how quickly you can develop them, how effectively you can test them, and how smoothly you can deploy and interact with them. Foundry is a modern smart contract development framework built on top of dap tools, and today we’ll explore how to use it. To start a new Foundry project, you first need to download Foundry and Forge from the GitHub repository. By visiting the Foundry ETH repo, you can install Foundry using a single curl command, after which running `foundryup` in your terminal will install Forge and Cast tools, setting you up for development. All the code we’ll be working with is available on my GitHub repository called Foundry Play, with a link in the description. For those interested in more advanced usage, the Foundry Starter Kit public template offers extensive features, including advanced testing, scripts, and seamless integration with Chainlink smart contracts, making it easy to get started immediately. Another exciting resource is the Foundry book, which provides a comprehensive guide, similar to the Rust book, covering everything needed to master Foundry.

Some of Foundry’s main advantages include speed, built-in fuzz testing, Solidity-based testing capabilities, and a suite of EVM test utilities. Its scripts and tests are primarily written in Bash or shell scripts, offering a developer experience similar to dap tools but with even faster performance. The built-in fuzzing and shell scripting simplify development, testing, and deployment, and if you prefer to avoid JavaScript or Python, mastering Bash with Foundry could be ideal. To create a new project, you run `forge init` in your terminal, which generates a project structure including a `lib` folder for dependencies, a `src` folder equivalent to the `contracts` folder in other frameworks, and a `test` folder for Solidity-based tests. For example, the `DSTest.sol` contract included is a comprehensive testing library with utilities that we’ll explore. Running `forge test` compiles your contracts and runs your tests, providing useful feedback such as gas consumption metrics.

The `.gitignore` file excludes irrelevant files like Git submodules, which are used to pull in external repositories into the `lib` folder, and the `foundry.toml` config file allows customization of the project’s settings with links for more documentation. After this overview, let’s dive into writing and understanding Solidity tests and built-in fuzzing.

We start by creating a new contract called `StakeContract.sol`. Initially, compiling it with `forge build` throws an error because the OpenZeppelin contracts dependency isn’t installed. Foundry automatically installs dependencies from GitHub repos via the `forge install` command. For OpenZeppelin, running `forge install OpenZeppelin/openzeppelin-contracts` downloads the library into the `lib` folder and adds it as a Git submodule, as confirmed by checking `.gitmodules`. However, even after installing, the compiler needs remappings to resolve imports correctly. By editing the remappings file to map `@openzeppelin` to the corresponding path in `lib/openzeppelin-contracts/`, the compiler can locate the dependencies, and the build succeeds.

Next, we implement a simple staking contract with a mapping to track balances for each user and a `stake` function that accepts an amount and a token address. The function updates the user’s balance and transfers tokens from the user to the contract, reverting with a custom error if the transfer fails. After fixing a minor syntax issue, the contract compiles successfully.

To test this contract, we create `StakeContract.t.sol`, which inherits from `DSTest` to access built-in testing utilities and cheat codes. We also create a mock ERC20 token contract (`MockERC20.sol`) for testing purposes, which is small and simple. The test setup function initializes instances of both the staking contract and mock token. A basic test involves approving the staking contract to spend tokens on behalf of the user and then calling the `stake` function, asserting it returns true. After correcting naming inconsistencies, the test passes.

One of Foundry’s powerful features is its built-in fuzz testing, which automatically runs your test with many randomized inputs to discover edge cases or failures. By adding a parameter to the test function, Foundry tests the staking logic with a wide range of amounts. For example, testing with `uint256` often finds failures when amounts exceed balances, while using `uint8` limits values and tends to pass more often. This automated fuzzing acts like chaos testing, identifying unexpected failures that developers might overlook.

Another valuable feature is Foundry’s cheat codes, which allow you to manipulate the blockchain environment during testing. By importing a `Cheats.sol` abstract contract, you gain access to functions that can change block timestamps, numbers, memory storage, expect events, and trigger reverts, all within your Solidity tests. These cheat codes enable simulating different scenarios and blockchain states, significantly enhancing test coverage and reliability.

Beyond testing and building contracts, Foundry facilitates scripting for deployment and interaction with smart contracts. Most scripts use Bash or shell languages, often coordinated through a Makefile. The Makefile bundles commands such as installing Solidity versions, cleaning builds, updating dependencies, and compiling contracts. Running `make` automates these steps, ensuring the environment is correctly set up. To deploy locally, you can spin up a local blockchain node using Hardhat. Installing Hardhat with Yarn or npm and running `hardhat node` creates a local blockchain on your machine. You then deploy contracts to this local node using `forge create`, specifying private keys and RPC URLs as needed.

Once deployed, the local blockchain logs transactions and contract deployments, allowing for immediate interaction and testing. Foundry’s GitHub repository is actively maintained with frequent updates, making it an excellent choice for fast, flexible, and powerful smart contract development. I highly recommend exploring the Foundry Starter Kit for more advanced use cases and integration examples. Foundry’s combination of speed, Solidity-native testing, fuzzing, cheat codes, and simple scripting makes it a robust framework that can elevate your smart contract development workflow. Have fun experimenting with Foundry, and I look forward to seeing what you build!
