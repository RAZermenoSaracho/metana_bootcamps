# Ownable

An explanation of ownable, how to restrict functions that perform sensitive state changes to only a single privileged address.

The Ownable contract is commonly used to secure smart contracts by ensuring that functions performing sensitive state changes are protected, allowing only privileged addresses to invoke them. It’s a simple concept, but instead of implementing it ourselves, we can use OpenZeppelin’s battle-tested contract right out of the box. As shown in the code snippet, by extending Ownable, you can call its constructor with an initialOwner parameter, and any function with the onlyOwner modifier can only be called by the contract owner. Let’s start by implementing our own contract called ContractWithOwner, which will extend the Ownable contract. We’ll define a constructor with no parameters, but since we’re extending Ownable, we need to pass the initialOwner parameter to the Ownable constructor. We’ll set the contract deployer as the initial owner by passing msg.sender. To illustrate the difference between protected and unprotected functionality, we’ll create two state variables: a protectedCount (public, defaulting to zero since no value is set) and an unprotectedCount. Next, we’ll create two setter functions. The protectedFunction takes a new count, uses the onlyOwner modifier (available via the Ownable contract), is marked as external, and assigns the new value to protectedCount. The second function, unprotectedFunction, is identical but omits the onlyOwner modifier, allowing any external address to call it and update unprotectedCount.

I’ve already set up the unit tests in Hardhat to save time for this video. We have a deployment fixture to configure everything before running the tests. The tests include: verifying that the contract deployer is the owner, ensuring the owner can call the protected function, confirming non-owner addresses cannot call the protected function, and checking that anyone can call the unprotected function. Another test ensures that transferring ownership to the zero address (an invalid address) reverts, as the Ownable contract’s transferOwnership function is designed to require a valid address to take control. The renounceOwnership function, however, allows the owner to transfer ownership to the zero address to effectively renounce it. We also test that ownership can be successfully transferred to another valid address, the new owner can call the protected function, and a non-owner cannot renounce ownership. Finally, we verify that after renouncing ownership, the owner becomes the zero address.

Let’s examine the Ownable contract code. The transferOwnership function expects a valid address to take control, so attempting to transfer to the zero address reverts, as it’s inaccessible. Conversely, renounceOwnership achieves its purpose by setting the owner to the zero address. Now, let’s run the unit tests using npm run test.
