# AccessControl

Explanation of role based access control using Openzepplin access control contract

[Video: OpenZeppelin by Example - AccessControl](https://www.youtube.com/watch?v=J4mhJUTfgNs)

**Transcript for the AI**

Hello everyone, and welcome back to our OpenZeppelin tutorial series. In this video, we’ll explore role-based access control using OpenZeppelin’s AccessControl contract. In our previous videos, we covered the Ownable contracts, which assign a single owner to control all privileged functionality in a contract. However, AccessControl allows us to define multiple roles, each permitted to perform specific sets of actions, providing more granular control and distributing privileges across multiple addresses. As noted in the OpenZeppelin documentation, for each role you want to define, you create a unique role identifier using a bytes32 variable, typically set to the keccak256 hash of the role’s name. For example, a MINTER\_ROLE might be defined for an ERC-20 token to designate an address responsible for minting new tokens. Another example includes both a MINTER\_ROLE and a BURNER\_ROLE, further distributing privileges. This approach aligns with the principle of least privilege, a key security practice that ensures no single address has more authority than necessary, especially for complex or sensitive functionality. By default, accounts with a role cannot grant or revoke that role for others; they can only perform the actions associated with it. To manage roles dynamically, you need an admin role, and each role can have its own admin, allowing for even finer-grained control and enhanced security. This means a rogue address is limited to the scope of its assigned role, reducing the risk of widespread damage. Before diving into the code, I need to mention a new dependency: dotenv for managing environment variables. Hardhat recently introduced native support for this, but I’ll use dotenv for simplicity. If you try these unit tests yourself, you can copy the sample .env file from the repository and add your RPC URL. I’m using Alchemy’s free tier for this, though I’m not sponsored—it’s just user-friendly with a good quota. I’ll also link to free RPC providers in the description if you prefer not to sign up for Alchemy or similar services. If the RPC key is undefined, the other tests in the repository will still run without issues.

Now, let’s examine the AccessControl contract. The onlyRole modifier ensures that only addresses with a specific role can execute a function. You can check if an account has a role, retrieve the admin role for a given role, and have admins grant or revoke roles. Additionally, any address with a role can renounce it if they no longer want that privilege. For today’s example, we’ll create a relatively simple contract to handle deposits and withdrawals of ERC-20 tokens, with pause functionality controlled by a PAUSER\_ROLE. Since we’re dealing with ERC-20 token transfers, we’ll use OpenZeppelin’s SafeERC20 contract for the ERC-20 interface to ensure safe transfers. We’ll define two events: Deposit, which emits the account and token amount (with the account indexed for easier filtering on the blockchain), and Withdrawal, with the same structure. We’ll also include a custom error, InsufficientFunds, for cases where a withdrawal exceeds the available balance. Next, we define a bytes32 constant, PAUSER\_ROLE, set to the keccak256 hash of the string “PAUSER”. In the constructor, we pass the pauser’s address, grant the DEFAULT\_ADMIN\_ROLE to the contract deployer (msg.sender), and assign the PAUSER\_ROLE to the specified pauser address. To track ERC-20 token balances, we create a private mapping of accounts to another mapping of tokens to balances, and provide a public getter function, balance, to allow off-chain queries of an account’s balance for a specific token.

For the deposit function, we allow anyone to call it (when not paused) with parameters for the token and amount. Using SafeERC20, we cast the token to the IERC20 interface and call safeTransferFrom to transfer tokens from the sender to the contract address. If the transfer succeeds, we update the balance mapping for the sender and token, incrementing it by the deposited amount, and emit the Deposit event. The withdraw function is similar but includes a receiver address, allowing the account to withdraw to another address. It’s also restricted to when the contract is not paused. We first check if the sender’s balance for the token is sufficient, reverting with InsufficientFunds if not. To prevent reentrancy vulnerabilities, we decrement the balance before calling safeTransfer to the receiver, then emit the Withdrawal event. For pause functionality, we define pause and unpause functions, both restricted by the onlyRole(PAUSER\_ROLE) modifier, wrapping the pause and unpause functions from OpenZeppelin’s Pausable contract, which handles edge cases like attempting to pause an already paused contract. The balance getter function returns the balance for a given account and token, using the mapping.

I’ve prepared unit tests in advance. These verify that roles are set correctly on deployment, the pauser can pause and unpause the contract, deposits and withdrawals of Wrapped Ethereum (WETH) succeed when not paused but revert when paused, withdrawals revert if the balance is insufficient, the admin (deployer) can revoke the pauser’s role, and the pauser can renounce their role. To test with WETH, we fork Ethereum mainnet using the Hardhat config’s RPC URL. For each test involving ERC-20 deposits, we take the initial ETH provided by Hardhat’s test network, send it to the WETH contract’s deposit function to receive WETH, and use that for testing. Running npm run test shows all tests passing. The code is available in the GitHub repository linked in the description. I encourage you to clone it, add log messages, experiment, and play around with the tests. That’s all for this video, and I’ll see you in the next one!
