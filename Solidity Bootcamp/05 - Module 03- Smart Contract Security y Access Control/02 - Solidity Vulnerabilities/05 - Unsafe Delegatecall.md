# Unsafe Delegatecall

Explains what is delegatecall, the vulnerabilities lying in it and examples of vulnerable delegatecalls

[Video: Unsafe Delegatecall (part 1) | Hack Solidity (0.6)](https://www.youtube.com/watch?v=bqn-HzRclps)

**Transcript for the AI**

Hello everyone, in this video, I’ll demonstrate how to misuse the delegatecall function in Solidity, essentially showing you how to “shoot yourself in the foot” with unsafe usage. By examining smart contracts that misuse delegatecall, you’ll learn to recognize both safe and unsafe practices. This is part one of a two-part series: today, we’ll explore a simple example of unsafe delegatecall, and in the next video, we’ll cover a more sophisticated case. First, let’s briefly explain what delegatecall is. When Contract A uses delegatecall to call Contract B, it instructs Contract B to execute its code within Contract A’s context, using Contract A’s storage, msg.sender, msg.value, msg.data, and other contextual variables. Two key considerations are critical: first, delegatecall preserves the caller’s context, and second, the storage layout of both contracts must be identical, meaning Contract A and Contract B must declare the same state variables in the same order. Misusing these principles can lead to vulnerabilities, which we’ll explore in this video by focusing on the context preservation issue, and in the next video by examining mismatched storage layouts.

Consider a contract called HackMe, which has an owner state variable set to msg.sender in its constructor and a lib state variable pointing to another contract’s address, also set during construction. The HackMe contract has a fallback function that uses delegatecall to forward any non-existent function calls to the lib contract, passing along msg.data. The Lib contract has its own owner state variable and a function called pwn, which sets Lib’s owner to msg.sender. The challenge is to hijack HackMe by changing its owner state variable, despite no explicit function in HackMe allowing this. The vulnerability lies in the fallback function’s use of delegatecall. Since delegatecall executes Lib’s code in HackMe’s storage context, calling pwn on Lib via HackMe’s fallback will modify HackMe’s owner. To exploit this, we create an Attack contract that stores the HackMe contract’s address in a state variable, set via the constructor. The Attack contract has an attack function that calls HackMe with the function signature of pwn using hackMe.call(abi.encodeWithSignature(“pwn”)). Since pwn doesn’t exist in HackMe, the fallback function triggers, delegating the call to Lib, which executes pwn and sets HackMe’s owner to msg.sender (the Attack contract).

Let’s see this in action in Remix. Alice (account 1) deploys the Lib contract, then uses its address to deploy the HackMe contract, setting HackMe’s owner to herself. Eve (account 2) deploys the Attack contract, passing HackMe’s address. We verify that HackMe’s owner is initially Alice. Eve then calls Attack’s attack function, which triggers HackMe’s fallback via a call to pwn. This delegates to Lib, executing pwn in HackMe’s context, setting HackMe’s owner to the Attack contract’s address. Checking HackMe’s owner again confirms it’s now the Attack contract, demonstrating the successful hijack. This exploit highlights the danger of misusing delegatecall when forgetting that it preserves the caller’s context. In the next video, we’ll explore issues arising from mismatched storage layouts between contracts. Thanks for watching, and see you later!
