# Front Running

Explains what front running and showcases a piece of code that is vulnerable to front running

[Video: Front Running | Hack Solidity (0.6)](https://www.youtube.com/watch?v=MN55R440twQ)

**Transcript for the AI**

Your smart contract can have zero bugs and still be vulnerable to other attacks. One of these is called front-running. In this video, we’ll explore what front-running is and examine a piece of code that is vulnerable to it. First, let’s understand how a transaction is included in a block. Suppose we have Alice, Eve, and some miners. Alice sends a transaction to the network, and it gets relayed to miners, who then place it in their transaction pool. This pool contains pending transactions that haven’t yet been included in a block. For example, Alice’s transaction might appear in one miner’s transaction pool. Each miner selects a set of transactions from their pool to include in the next block. Let’s say this miner chooses three transactions: the first one, Alice’s, and another one, to be mined in that order. If this miner successfully mines the block, those transactions, including Alice’s, are now recorded on-chain. Now, let’s understand how front-running works. Rewinding to the moment when Alice’s transaction is still sitting in the pool, Eve—who is monitoring the pool—spots Alice’s transaction and sends her own competing transaction. Eve’s transaction also propagates across the network and lands in the same transaction pool.

Suppose the miner picks Eve’s transaction before Alice’s, and then another transaction, to include in the next block. Even though Alice submitted her transaction first, Eve’s transaction gets included earlier because she offered a higher gas price. As a result, Eve’s transaction is processed before Alice’s. This is where the incentive for front-running comes in. For example, imagine Alice knows a secret that allows her to unlock 10 ether from a contract. She includes that secret in her transaction and broadcasts it. While Alice’s transaction is waiting in the mempool, Eve sees it, reads the secret, and sends a copycat transaction using the same secret but with a higher gas price. Since Eve’s transaction is mined first, she ends up claiming the 10 ether—even though Alice discovered the secret and submitted her transaction first. That’s how front-running works. Now let’s look at a vulnerable smart contract. The contract is called `FindThisHash`, and it holds 10 ether. The idea is that anyone who can find a string that hashes to a specific target hash is considered a winner and receives the reward. This contract is front-running vulnerable. Suppose Alice finds the correct preimage and sends a transaction to claim the reward. While her transaction is still in the mempool, Eve sees it, reads the solution, and sends her own transaction using the same string—but with a higher gas price. Eve’s transaction is mined first, and she claims the 10 ether. When Alice’s transaction is finally processed, the contract’s balance is already zero. This demonstrates that even if your contract is logically correct and bug-free, it can still be vulnerable to front-running if there’s economic incentive for transaction reordering.
