# Arithmetic Overflow and Underflow

Explanation of overflow and underflow, and how to protect a smart contract from it

[Video: Arithmetic Overflow and Underflow | Hack Solidity (0.6)](https://www.youtube.com/watch?v=zqHb-ipbmIo)

**Transcript for the AI**

Hello everyone, in this video, we’ll explore overflow and underflow vulnerabilities in Solidity smart contracts. I’ll first explain what overflow and underflow are, then examine a smart contract vulnerable to these issues, and finally demonstrate how to protect your code from such exploits. Overflow occurs when a number exceeds its maximum range, causing it to wrap around and start counting from zero, resulting in a smaller number than intended. Underflow is the opposite, happening when a number falls below the minimum range, wrapping around to the maximum value, yielding a larger number. For example, with the uint256 data type (unsigned integer), which ranges from 0 to 2^256 – 1, an overflow happens when a number exceeds 2^256 – 1. If a number is 3 beyond this maximum, Solidity wraps it around: 1 beyond lands at 0, 2 beyond at 1, and 3 beyond at 2, so the result is 2. Underflow works similarly; for a number like -2, Solidity counts backward from the maximum, landing at 2^256 – 2. Notably, Solidity (prior to version 0.8) provides no warnings or errors for these issues, so developers must be cautious. Let’s examine a vulnerable contract called TimeLock, which allows users to deposit ETH and withdraw it after a one-week lock period. It uses a balances mapping to track deposited ETH and a lockTime mapping to store the earliest withdrawal time. The deposit function updates the sender’s balance and sets lockTime to one week from the current time. The withdraw function checks that the sender has a balance greater than 0 and the current time exceeds their lockTime, then sends the ETH and resets the balance to zero. The increaseLockTime function adds a specified number of seconds to the sender’s lockTime.

This TimeLock contract is vulnerable to an underflow attack, allowing withdrawals before the one-week lock period. The attack exploits the increaseLockTime function by passing a large number to trigger an underflow. We’ll create an Attack contract to demonstrate this. It stores the TimeLock contract’s address in a state variable, set via the constructor. A payable fallback function receives ETH withdrawn from TimeLock. The attack function, marked payable, requires msg.value >= 1 ether, deposits 1 ETH into TimeLock using timeLock.deposit{value: 1 ether}(), setting the lockTime to one week from now, and then triggers the exploit. To bypass the lock, we calculate a number causing an underflow. If the current lockTime is T, we need X + T = 2^256, which wraps to 0 due to overflow. Solving for X, we get X = 2^256 – T. In Solidity, we pass -T (cast as uint256), which represents 2^256 – T, to increaseLockTime. We retrieve T with timeLock.lockTime(address(this)). This sets lockTime to 0, allowing an immediate call to timeLock.withdraw(). In Remix, we deploy TimeLock and Attack, with Eve (account 1) depositing 1 ETH into TimeLock. A direct withdrawal fails due to the lock period, but calling Attack.attack with 1 ETH succeeds, withdrawing the ETH immediately by setting lockTime to 0. Checking lockTime confirms it’s 0, proving the underflow.

To prevent overflow and underflow, we use OpenZeppelin’s SafeMath library. Import SafeMath from GitHub and add using SafeMath for uint256; to TimeLock. In increaseLockTime, replace lockTime[msg.sender] += secondsToIncrease with lockTime[msg.sender] = lockTime[msg.sender].add(secondsToIncrease). SafeMath’s add function checks for overflow and reverts if it occurs. Testing the attack again, we redeploy both contracts, call Attack.attack with 1 ETH, and the transaction fails with “SafeMath: addition overflow,” confirming the protection.
