# Reentrancy

Describes what a reentrancy attack is, showcases on how it occurs and presents how to prevent it

[Video: Reentrancy | Hack Solidity (0.6)](https://www.youtube.com/watch?v=4Mm3BCyHtDY)

**Transcript for the AI**

Hello everyone, welcome back to our series on hacking Solidity smart contracts. The purpose of this video is to explore how a smart contract can be hacked, helping you understand the security risks involved in writing Solidity code. I want to emphasize that this video does not encourage hacking smart contracts in the real world. Today, we’ll focus on the reentrancy attack: I’ll explain what it is, demonstrate it with Solidity code in Remix, and show techniques to prevent it. First, let’s define a reentrancy attack. Imagine two contracts: Contract A and Contract B. Contract A calls Contract B, and reentrancy occurs when Contract B calls back into Contract A while Contract A is still executing. To illustrate how this can be exploited, suppose Contract A holds 10 ETH and tracks balances, including 1 ETH owed to Contract B, while Contract B has 0 ETH. Contract A has a withdraw function that checks if the caller has a sufficient balance, sends the owed ETH, and then sets the caller’s balance to zero. For example, if Alice has 1 ETH stored in Contract A and calls withdraw, it verifies her balance, sends her 1 ETH (reducing Contract A’s balance to 9 ETH), and sets her balance to zero. Now, consider how Contract B can exploit this. Contract B needs two functions: a fallback function and an attack function, both calling withdraw on Contract A. The attack works as follows: Eve calls Contract B’s attack function, which triggers withdraw on Contract A. Contract A checks Contract B’s balance (1 ETH), sends 1 ETH to Contract B, triggering Contract B’s fallback function. The fallback function calls withdraw again, and since Contract A hasn’t updated Contract B’s balance yet, the check passes, sending another ETH. This loop continues, allowing Contract B to drain Contract A’s ETH because the balance update occurs after the external call.

Let’s see this in action in Remix with a contract called EtherStore. This contract allows users to deposit ETH via a deposit function, which updates a balances mapping, and withdraw ETH via a withdraw function, which checks the caller’s balance, sends the ETH, and sets the balance to zero. It also has a getBalance helper function to return the contract’s total ETH. We’ll create an Attack contract to exploit EtherStore. It stores the EtherStore contract’s address in a state variable, set during deployment. The Attack contract has a fallback function and an attack function. The attack function requires msg.value >= 1 ether, deposits 1 ETH into EtherStore using etherStore.deposit{value: 1 ether}() (Solidity 0.6 syntax, as opposed to Solidity 0.5’s .value(1 ether)), and immediately calls etherStore.withdraw(1 ether). This triggers EtherStore’s withdraw, which sends 1 ETH back to Attack, activating the fallback function. The fallback function checks if EtherStore has at least 1 ETH (address(etherStore).balance >= 1 ether) and calls withdraw again, creating a loop. A helper function, getBalance, shows the ETH accumulated by Attack. In Remix, we deploy EtherStore and Attack, assigning 1 ETH to Alice and 1 ETH to Bob in EtherStore (total 2 ETH). Using Eve’s account, we call attack with 1 ETH, successfully stealing 2 ETH from EtherStore, leaving it with 0 ETH and Attack with 3 ETH (1 deposited + 2 stolen). Debugging in Remix with breakpoints reveals the execution: attack deposits 1 ETH, calls withdraw, which sends 1 ETH, triggering fallback. The fallback calls withdraw again, and since the balance isn’t updated until the end, EtherStore sends another ETH, repeating until EtherStore has 0 ETH.

To prevent reentrancy attacks, I’ll show two techniques. First, update state variables before making external calls. In EtherStore’s withdraw function, move the balance update (balances[msg.sender] = 0) before the ETH transfer. This ensures that when the fallback function calls withdraw again, the balance is already zero, causing the check to fail and preventing further withdrawals. Second, use a reentrancy guard modifier, nonReentrant. This requires an internal state variable, bool private locked, to track whether the contract is locked. The nonReentrant modifier checks require(!locked, “ReentrancyGuard: reentrant call”), sets locked = true, executes the function, and then sets locked = false. Applying nonReentrant to the withdraw function ensures that if an attacker calls withdraw again before the first call completes, the locked check fails, halting the transaction. For example, when the attacker calls withdraw, the modifier sets locked = true, executes the function, and sends ETH, triggering the fallback. If fallback calls withdraw again, the locked = true check fails, stopping the attack. These techniques—updating state before external calls and using a reentrancy guard—effectively prevent reentrancy attacks.
