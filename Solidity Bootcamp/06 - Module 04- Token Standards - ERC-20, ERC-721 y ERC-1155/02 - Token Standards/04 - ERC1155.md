# ERC1155

Delves into implementing an ERC-1155 contract. Demonstrates key functions such as `mintBatch`, `transferBatch`, and how balances are tracked per token ID. It also covers how ERC1155 uses a single smart contract to manage multiple token IDs, and likely touches on the interface functions like uri and the safe transfer rules (including onERC1155Received hook).

**Transcript for the AI**

Today, we’ll be coding an ERC-1155 contract, which manages multiple tokens within a single contract. We’ll start by importing the necessary interfaces: IERC1155, which defines the ERC-1155 standard, and IERC1155Receiver, which includes the onERC1155Received and onERC1155BatchReceived functions called when tokens are transferred to a contract recipient. I’ll explain these callbacks later. We’ll create a base contract named ERC1155 that implements IERC1155, and a separate contract, MyMultiToken, that inherits from ERC1155 to add mint, batchMint, burn, and batchBurn functions, which are not part of the ERC-1155 standard. In the ERC1155 contract, we begin by copying all functions from the IERC1155 interface and converting their declarations into function bodies to resolve compilation errors. Next, we define the required events: TransferSingle, TransferBatch, ApprovalForAll, and URI. For state variables, we create a public mapping, mapping(address => mapping(uint256 => uint256)) public balanceOf, to track the balance of each token ID for each owner. We also define a public mapping, mapping(address => mapping(address => bool)) public isApprovedForAll, to store whether an operator is approved to manage all tokens of an owner, satisfying the isApprovedForAll function requirement. Compilation errors for balanceOf and isApprovedForAll are resolved by these public mappings, so we remove their redundant function declarations.

For metadata, we implement supportsInterface, which returns true if the provided interfaceId matches IERC165, IERC1155, or IERC1155MetadataURI, indicating supported interfaces. We also include the uri function for metadata, but these are less critical, so let’s focus on the core functionality. We start with an internal mint function, \_mint(address to, uint256 id, uint256 value, bytes memory data), which updates the balance and handles contract recipients. It requires to != address(0) with the error “to is zero address”, increments balanceOf[to][id] += value, and emits a TransferSingle event with emit TransferSingle(msg.sender, address(0), to, id, value). If to is a contract (to.code.length > 0), we call IERC1155Receiver(to).onERC1155Received(msg.sender, address(0), id, value, data), ensuring the returned bytes4 matches IERC1155Receiver.onERC1155Received.selector, or revert with “unsafe transfer”. The internal batchMint function, \_batchMint(address to, uint256[] memory ids, uint256[] memory values, bytes memory data), mints multiple tokens. It requires to != address(0) and ids.length == values.length (“ids not equal to values length”). A for loop updates balanceOf[to][ids[i]] += values[i] for each token, emits a TransferBatch event with emit TransferBatch(msg.sender, address(0), to, ids, values), and, if to is a contract, calls IERC1155Receiver(to).onERC1155BatchReceived(msg.sender, address(0), ids, values, data), verifying the selector or reverting.

In MyMultiToken, we define external mint(address to, uint256 id, uint256 value, bytes memory data) and batchMint(address to, uint256[] memory ids, uint256[] memory values, bytes memory data) functions, calling \_mint(msg.sender, id, value, data) and \_batchMint(msg.sender, ids, values, data), respectively. Next, we implement internal burn functions. The \_burn(address from, uint256 id, uint256 value) function requires from != address(0) (“from is zero address”), decrements balanceOf[from][id] -= value, and emits TransferSingle(msg.sender, from, address(0), id, value). The \_batchBurn(address from, uint256[] memory ids, uint256[] memory values) function requires from != address(0) and ids.length == values.length, uses a for loop to decrement balanceOf[from][ids[i]] -= values[i], and emits TransferBatch(msg.sender, from, address(0), ids, values). In MyMultiToken, we add external burn(address from, uint256 id, uint256 value) and batchBurn(address from, uint256[] memory ids, uint256[] memory values), calling their internal counterparts.

We then implement balanceOfBatch(address[] memory owners, uint256[] memory ids), which returns an array of balances for multiple owners and token IDs. We initialize uint256[] memory balances = new uint256[](owners.length), require owners.length == ids.length (“owners not equal to ids length”), and use a for loop to set balances[i] = balanceOf[owners[i]][ids[i]], returning balances. The setApprovalForAll(address operator, bool approved) function sets \_isApprovedForAll[msg.sender][operator] = approved and emits ApprovalForAll(msg.sender, operator, approved). For safeTransferFrom(address from, address to, uint256 id, uint256 value, bytes memory data), we require msg.sender == from || \_isApprovedForAll[from][msg.sender] (“not approved”) and to != address(0), update balanceOf[from][id] -= value and balanceOf[to][id] += value, emit TransferSingle(msg.sender, from, to, id, value), and, if to is a contract, call onERC1155Received as before. Similarly, safeBatchTransferFrom(address from, address to, uint256[] memory ids, uint256[] memory values, bytes memory data) requires the same checks, including ids.length == values.length, updates balances in a for loop, emits TransferBatch, and calls onERC1155BatchReceived if needed.
